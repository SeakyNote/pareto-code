## 2. 原始需求与方案依据

主要依据为 [AI 应用大赛参赛方案介绍](../方案/AI应用大赛参赛方案介绍.md)，以及 `方案/image.png`、`方案/Pasted image 20261101153653.png` 两张参考图片。

项目名称为“基于帕累托前沿的 AI 应用效费比评估与智能选型系统”，面向公司内部使用付费 AI 的员工，综合比较：

- **任务效果**：模型或 Agent 在指定任务集、指定评分规则下的表现，越高越好。
- **调用费用**：统一费用口径下的每任务成本，越低越好。
- **执行耗时**：从任务发起到返回完整结果的时间，越短越好。

候选配置包含 Agent、基础模型及版本、推理强度、供应商和使用渠道等维度。用户选择工作场景并填写预算、可接受耗时等条件后，系统展示帕累托前沿及分档推荐，最终由用户选择配置。

方案覆盖代码开发、SVG 绘图、办公自动化、文档编写与审查。MVP 优先完成至少一个核心场景，其余场景按需扩展。

方案还提出结合第三方评测和自建测试集、保留来源与评测时间、探索 AI 辅助评分与解释，并以实测对比验证降本效果。方案中“成本减少一半以上”属于待验证的预期，当前实现没有证明这一节约比例。

## 3. 本次 MVP 的实现结果

### 3.1 技术与交付方式

本次在当前仓库实现了本地 B/S 应用，采用：

- Node.js 内置 HTTP 服务。
- Node.js 内置 `node:sqlite` 与 SQLite 持久化。
- 浏览器原生 HTML、CSS、JavaScript ES Modules。
- SVG 交互图表。

运行时没有第三方依赖，无需安装前端构建工具、无需 API Key。开发时参考了 Sites 技能的本地开发与验证流程，交付结果保存在仓库中，未发布到外部托管服务。

### 3.3 数据与比较口径

仓库最初只有方案和原型截图，没有可直接导入的原始评测数据。因此本次内置数据为**人工构造的演示快照**，统一标记为 `source.type=demo`，不代表真实模型能力、官方价格或真实节约效果。

真实选型需要导入有依据的实测结果。系统根据导入者声明的元数据划定比较范围，不会自动验证第三方数据的真实性，也不会证明两套评分标准等价。

主要规则如下：

1. 只在同一评测快照、同一渠道内比较，快照统一声明场景、任务集、评分、聚合、耗时、费用及币种口径。
2. API 采用所有任务（包括失败任务）的每任务平均费用和平均完整执行耗时。
3. API 与会员订阅分别计算前沿，USD 与 CNY 不隐式换汇或混合比较。
4. 缺少效果、API 费用、完整耗时或样本数的记录保留展示，但排除计算；未知费用不能用零替代，零费用本身有效。
5. 非完整执行时间、非所有任务均值、非每任务费用，以及缺少可追溯链接的第三方数据，会注明排除原因。
6. 导入采用事务整体保存；预览不写入，重复快照 ID 不覆盖，也不向已有快照追加配置。
7. 默认按评测时间优先展示最新快照，超过 30 天提示复测。
8. 没有满足条件的配置时展示空推荐和违反的条件，不自动放宽要求。

会员费用采用用户输入的假设：

```text
每任务订阅均摊费用 = 月订阅费 ÷ 每月有效任务量
```

初始月费 20、月任务量 400 仅为演示输入，不是会员官方报价。均摊费用不等于单次任务的新增支出，也不保证调用配额、排队或超额费用。

### 3.4 算法与推荐解释

配置 A 支配配置 B，当且仅当：

```text
A.任务效果 >= B.任务效果
A.每任务费用 <= B.每任务费用
A.完整执行耗时 <= B.完整执行耗时
并且至少有一项严格更优。
```

没有被其他配置支配的配置组成前沿，三项指标完全相同的配置互不支配。前沿采用确定性计算，复杂度为 O(n²)。

推荐先满足用户约束，再从可行前沿中选择：

- 经济档：费用最低；同价时优先耗时更短，再考虑效果。
- 效果档：效果最高；同分时优先费用更低，再考虑耗时。
- 偏好档：对效果、费用和速度做区间归一化，按显式权重选择。

| 推荐偏好 | 效果权重 | 费用权重 | 速度权重 |
| --- | ---: | ---: | ---: |
| 综合权衡 | 50% | 25% | 25% |
| 效果优先 | 80% | 10% | 10% |
| 节省费用 | 25% | 65% | 10% |
| 更快完成 | 25% | 10% | 65% |

权重只影响偏好推荐，不改变帕累托前沿。解释由本地规则生成，页面没有将其表述为实际模型推理。

图中圆环表示包含耗时的三目标前沿；虚线只表示当前两个维度的投影包络，二者含义不同。对数坐标采用 `log1p` 变换保留零费用，仅改变显示位置，不改变计算。

### 3.5 当前版本的边界

当前版没有内置真实任务集与评分器，没有逐题评分证据核验，也没有惯用配置基准与同质量月度节省测算。

自动付费评测执行、外部榜单抓取、实时价格与汇率、AI 主观判分、账号权限、配额管理和真实降本比例验证均未接入。它适合本地演示及受信任环境中的试用。

## 4. 与 `one_shot` 分支的差异

代码对比发现：`one_shot` 更完整地覆盖自建评测与降本测算；`one_shot_2` 更侧重选型交互和完整评测快照管理。两者各有已完成的功能，当前版本不能视为全面覆盖 `one_shot` 的升级。

| 对比项 | `one_shot`（fa3e60e） | `one_shot_2`（162d7d5） |
| --- | --- | --- |
| 技术栈 | Python 3.11+、SQLite、原生前端 | Node.js 22.13+、SQLite、原生前端 |
| 默认启动地址 | `http://127.0.0.1:8000` | `http://127.0.0.1:3000` |
| 核心场景 | 固定为 Python 代码审查 | 初始为代码缺陷修复演示，支持导入其他三个场景 |
| 自建评测 | 内置 8 道代码审查题，可下载任务、提交实际运行日志、评分并入库 | 直接导入汇总指标，没有内置任务集与评分器 |
| 评分证据 | 保存逐题原始输出、起止时间和费用，重新核验评分与汇总一致性 | 校验汇总字段及口径，不复算逐题证据 |
| 节省测算 | 选择惯用配置，仅在效果不降低且满足约束时估算月度节省金额及比例 | 展示满足条件的最低费用，没有基准与月度节省测算 |
| 均衡推荐 | 选择三项指标中最大归一化差距最小的配置，无显式偏好权重 | 归一化后加权，支持综合、效果、费用和速度四种偏好 |
| 配置比较 | 以表格中的一个配置作为费用测算基准 | 最多固定 5 个配置并排比较，刷新后恢复 |
| 图表 | 线性坐标，按前沿、被支配和不满足约束着色；点击查看详情 | 增加对数坐标、二维包络和图表仅前沿开关，按模型系列着色；点击加入对比 |
| 数据组织 | 单条记录保存来源与时间，按任务集、评分、渠道、数据性质等自动分组 | 整套快照共享来源、评测时间及比较口径，每套快照独立选择 |
| 历史处理 | 同组同配置自动使用最新记录；最新记录缺指标时也不回退旧数据 | 选择整套快照，不自动拼接各配置的最新记录 |
| 订阅折算 | 每条配置保存自己的月费，用户调整月任务量 | 用户统一输入月费和月任务量，应用于当前订阅快照 |
| 币种与分数 | 固定人民币、0–100 分 | 支持 USD / CNY，评分上限由快照定义 |
| 批量导入 | 每次最多 500 条，支持单条配置追加 | 每次最多 2000 条、20 个快照，有独立导入历史；已有快照不能追加或覆盖 |
| 导出 | JSON 选型报告、CSV 对比表、原始 JSON / CSV | Markdown 选型报告、原始快照 JSON；CSV 用于导入模板，尚无结果 CSV 导出 |
| 需求交互 | 一句话规则填写，修改条件后自动重新计算 | 手动提交条件，筛选参数保存到 URL，修改条件后需重新分析才能导出报告 |
| 数据新鲜度 | 按配置自动选取最新记录 | 按快照评测时间排序，并对超过 30 天的快照提示复测 |

`one_shot` 的固定测试集为 `code-review-v1`，包含 8 道题，其中 2 道无缺陷题。它按缺陷“行号 + 类型”计算逐题 F1，再取均值乘以 100；误报、漏报和错误定位均影响分数。任务仍需人工在待测模型或 Agent 中执行，评分器不执行模型生成的代码。

两者共同具备三目标帕累托筛选、约束判断、JSON / CSV 导入、SQLite 持久化、来源说明、API 与订阅隔离及演示数据标记。两者都尚未自动调用付费模型或进行 AI 主观评分。

功能差异来自实现范围。评分器、节省测算可以用 Node.js 实现；当前版的图表、固定对比和筛选交互也可以连接 Python 后端。两个分支的数据结构与 API 不同，原始数据文件和数据库需要转换后才能互用。

## 5. 技术栈讨论与建议

### 5.1 对本项目的推荐

在没有团队语言偏好限制的前提下，对本项目长期方向的建议为：

**Python 后端 + JavaScript 前端 + SQLite。**

理由是后续重点更可能落在任务集维护、评测编排、评分证据、数据清洗、重复评测、统计分析与节约效果验证上。Python 的数据处理生态与这些工作较为贴合；需要时可以接入 pandas 等工具处理分组、缺失数据和时间序列，参见 [pandas 官方概述](https://pandas.pydata.org/docs/getting_started/overview.html)。

Node.js 的主要优势是前后端统一使用 JavaScript。如果维护团队主要熟悉 JavaScript / TypeScript，继续用 Node.js 也是合理选择，无需仅为更换语言而重写业务功能。

### 5.2 比较时需要区分的问题

| 维度 | 对话中的判断 |
| --- | --- |
| 评测与统计扩展 | 本项目长期更适合优先考虑 Python，属于结合业务方向的工程建议 |
| 前端交互 | 两种后端都能支撑相同的 JavaScript 图表与页面，界面效果不由后端语言决定 |
| 维护成本 | Python 方案需要维护 Python 和 JavaScript；Node.js 可统一前后端语言 |
| MVP 启动 | 两个实现均无运行时第三方依赖，均可本地启动 |
| 性能 | 没有可直接比较的负载测试，不能仅凭语言断言谁更快 |
| 功能完整度 | 应检查具体实现，不能把已有评分器或缺少评分器归因于语言能力 |

### 5.3 建议的后续路线（尚未执行）

1. 以 `one_shot` 的评测、逐题证据核验、比较逻辑和同质量节省测算为业务基础。
2. 吸收当前版的五项固定对比、对数坐标、筛选 URL 复现和快照管理等交互；推荐规则与快照策略存在差异，融合前需明确取舍。
3. 制定统一数据模型与 API，转换字段、币种和快照语义，并保留逐题证据。
4. 正式部署时，将 Python 标准库 HTTP 服务替换为适当的 Web 服务框架，例如 FastAPI，并完善实际部署所需的工程能力。

Python 官方明确不建议将 `http.server` 用于生产环境，参见 [官方说明](https://docs.python.org/3/library/http.server.html)。框架部署可参考 [FastAPI 部署文档](https://fastapi.tiangolo.com/deployment/)。上述建议不等于迁移已经完成。

## 7. 启动与后续查阅

### 7.1 `one_shot_2`

在当前分支、具备 Node.js 22.13 或更新版本的环境中执行：

```bash
npm start
```

访问 `http://127.0.0.1:3000`。数据库默认保存在 `.data/pareto.sqlite`。可参考 `.env.example` 配置 `HOST`、`PORT`、`DATABASE_PATH`。

```bash
npm run dev
npm run check
npm test
```

应用正常启动不需要 Playwright；浏览器检查需要另外具备 Playwright 和 Chromium：

```bash
npm run test:browser
```

该检查使用独立内存数据库，不改写本地评测工作库。桌面和手机截图输出到被忽略的 `test-results/` 目录。首次实现时临时启动的预览服务已在验证后停止，使用时需自行启动服务。

### 7.2 `one_shot`

以下命令需在 `one_shot` 分支或其独立检出目录执行，要求 Python 3.11 或更新版本：

```bash
python3 -m pareto.server
```

访问 `http://127.0.0.1:8000`。数据库默认保存在 `var/pareto.sqlite3`。该分支支持指定端口、数据库，以及首次创建数据库时不添加演示记录：

```bash
python3 -m pareto.server --port 8080 --db var/my-team.sqlite3
python3 -m pareto.server --no-demo --db var/real-only.sqlite3
```
